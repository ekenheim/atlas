# Decisions and spec deviations

Deviations from `hindsight_investment_research_build_plan.md` v1.1, and decisions the spec left open. ADRs for hard-to-reverse architectural choices live in `docs/adr/`.

## 2026-09-28: charting session (`.scratch/atlas-pilot/map.md`)

- **Pilot auth (deviates from §11, §13.3, Appendix A).** The cluster has no Authentik forward-auth/OIDC pattern on internal routes. For the pilot, Atlas uses the cluster's standard private-CIDR Envoy `SecurityPolicy`, with the actor identity taken from config (as in local dev). Every mutation still records an actor and an audit event. Authentik is post-pilot.
- **All LLM traffic via LiteLLM, including Atlas Hindsight (tightens §6.1).** Unlike the shared `llm/hindsight` release, which calls `openai-codex` directly, the dedicated Atlas Hindsight's extraction and reflect models are LiteLLM routes. The extraction model is chosen by a bake-off among already-paid options (MiniMax, self-hosted, and the subscription routes if their terms allow it) rather than a new paid API.
- **The CI gate before the GitHub remote exists (§14 Phase 0).** One local entrypoint runs lint, types, migrations and fixture-only tests; the GitHub Actions workflow calls the same entrypoint. The remote `ekenheim/atlas` is added before Phase 2.
- **Embeddings (§6.1).** Reuse `qwen3-embedding-0.6b` via LiteLLM (1024 dims), the same as the shared Hindsight.
- **Release-driven deployment (refines §12, Appendix A).** The app lives in its own GitHub repo under `github.com/ekenheim`. Versioned releases publish images to GHCR, and the home-ops deployment pins a released version and is bumped per release, never tracking `main`. Home-ops holds only manifests.
- **Issue tracking.** Local markdown under `.scratch/`, permanently (see `docs/agents/issue-tracker.md`).

## 2026-09-28: Hindsight 0.10.1 feature matrix (`docs/hindsight-feature-matrix.md`)

- **Provenance resolution (refines §6.4):** reflect citations carry no `document_id`. Atlas resolves observations through `source_memory_ids` to world facts, then maps each world fact to its Source Version via `document_id` (`srcv:<sha256>`) and the preserved `metadata.source_version_id`. Content that reflect draws from raw chunks, with no memory ID, is unverified until matched to an archived span.
- **Bank configuration uses versioned templates (§6.2):** 0.10.1 supports template export, dry-run and import, so the config-API fallback isn't needed.
- **Response schemas avoid union types:** 0.10.1 returns 500 on `"type": [..., "null"]`.
- **Worker slots ≥ 3:** consolidation reserves 2; pacing uses `HINDSIGHT_API_LLM_MAX_CONCURRENT`.

## 2026-09-28: models, pacing and Hindsight integration (tickets 05 and 07)

- **LLM:** MiniMax-M3 with thinking disabled for both extraction and reflect, behind the LiteLLM aliases `atlas-extract` / `atlas-reflect`. There is no fallback model; on 429 or an outage the ingest queue pauses with backoff. Routed models are recorded per run from LiteLLM `/model/info`.
- **Pacing:** Hindsight runs 2 concurrent LLM calls with 4 worker slots, and the backfill runs in a nightly window.
- **Document IDs** are per Source Version UUID and section (ADR-0001), which deviates from the spec's `srcv:<sha256>` example.
- **Only strict tag matching** is allowed through the gateway.
- **Citation states:** resolved / unverified / broken. Only resolved citations count as Evidence.
- **Phase 2 mental models:** Theme status and Bottlenecks, refreshed on a daily cron (not after consolidation). No knowledge pages in Phase 2.

## 2026-09-29: Hindsight in Compose, bank template and run record (build ticket 12)

- **Template file:** `configs/hindsight/bank-template.json` is `{template_version, manifest}`. The manifest goes to Hindsight unchanged. Each application records the version and the manifest's SHA-256 (`bank_template_application`) and writes a `bank_template.applied` audit event. A run's template version is the bank's latest application, and no run starts before one exists.
- **Template changes need a recording:** the contract test replays the real file through a recorded dry run and import. Changing the file means re-running `spikes/hindsight/record_bank_template.py` against the local spike (config-only, no LLM calls).
- **LiteLLM readiness** means Atlas's key is accepted by `GET /model/info` and every configured alias has a deployment. No model is called.
- **Routed models** are stored per alias as a list of `{model, model_id}` (`litellm_params.model`, `model_info.id`), since an alias can load-balance.
- **Local Hindsight** sits behind the Compose profile `hindsight`; CI never starts it. The app services read `ATLAS_COMPOSE_HINDSIGHT_URL`, which is separate from `.env`'s host-side `ATLAS_HINDSIGHT_URL`.
- **Code version** is the image's commit SHA (build arg `ATLAS_CODE_VERSION`, set by the release workflow), falling back to the package version.

Compose/CI use PGSTY Silo (a MinIO fork, pinned by digest; RustFS as fallback), verified for versioning, object lock and `If-None-Match` (ticket 13). Dev defaults to the filesystem backend.

## 2026-09-28: audit trail (ticket 03)

- **The database assigns the chain.** A BEFORE INSERT trigger on `audit_event` sets the gapless `id`, `occurred_at`, `prev_hash` and `event_hash` under a transaction-scoped advisory lock, so no code path can fork or forge the chain. Audit writers serialize until commit, so audited transactions must stay short. The hash format is documented in migration `0002`; `atlas audit verify` recomputes it independently in Python.
- **Append-only by trigger and by role.** Triggers (ENABLE ALWAYS) reject UPDATE, DELETE and TRUNCATE for every role, superusers included. Only the table owner can disable them, so the intended role split is: a migration role owns the schema and runs `atlas migrate`; the runtime role `atlas_app` (API, worker) holds only the privileges it needs, and on `audit_event` that is SELECT and INSERT. Migration `0002` grants these when `atlas_app` exists at migrate time; the deployment creates the role (and must re-run the grant if the role is created later). Later migrations should grant `atlas_app` the minimum on their own tables.
- **Tail truncation is out of the chain's reach.** Deleting the newest events (with the triggers disabled by the owner) leaves a valid shorter chain. `atlas audit verify` prints the head hash, so an external copy of it can detect this; anchoring it off-database is not built yet.
- **Content hashes are SHA-256 hex.** `old_hash` / `new_hash` must be 64 lowercase hex characters (a CHECK constraint), matching `raw_sha256` elsewhere.

## 2026-09-29: source ledger and ingest slice (ticket 07)

- **SEC's edge-injected `<script>` (the ticket 06 warning).** SEC's Akamai edge appends `<script type="text/javascript" src="/KSRe0…"></script>` to Archives HTML, and the token may vary between fetches. Decision:
  - **Raw bytes stay exactly as fetched.** `raw_sha256` hashes them, the archive stores them, and `GET /source-versions/{id}/content?kind=raw` returns them byte for byte, script included. Nothing is stripped before hashing.
  - **Change detection uses a second hash,** `comparison_sha256`: the SHA-256 of the raw bytes after the version's `comparison_rule` removed bytes that are not content. The rule `sec-edge-script-v1` applies to `sec_edgar` HTML (`text/html`, `application/xhtml+xml`) and removes every `<script …>…</script>` element (case-insensitive, non-greedy, on the bytes). Everything else uses `identity` (the raw hash). The rule is safe because EDGAR does not accept scripts or other active content in filed HTML documents, so a script in an Archives document can only come from SEC's serving layer, never from the filer.
  - A refetch whose raw hash differs but whose comparison hash matches the latest version's is **unchanged**: no new Source Version. The fetch observation keeps that fetch's own `raw_sha256`, and its exact bytes are archived (`fetch_observation.object_uri`), so nothing fetched is lost.
  - The parser drops script elements anyway, so the parse is unaffected either way.
  - Tested in `tests/integration/test_ingest.py::test_a_varying_sec_edge_script_alone_is_not_a_new_source_version` and `tests/unit/test_parsing.py::test_a_different_sec_edge_script_does_not_change_the_parse`.
  - A rule change is a new rule name. Versions keep the rule they were compared under, and a comparison only matches under the same rule.
- **Source Document identity is (provider, canonical URL), not the accession.** One EDGAR accession holds several documents (the 8-K and its EX-99.1), so `accession` is an indexed attribute, not unique (the data model had it unique). For SEC, the canonical URL (the accession's Archives folder plus the file name) is equivalent to (accession, document).
- **Per-fetch observations get their own table,** `fetch_observation` (append-only), resolving the data model's open point. Every fetch that returned or confirmed content is a row with its outcome (`new_version`, `unchanged`, `not_modified`), its hashes and its HTTP validators. The latest observation's validators make the next fetch conditional, so an unchanged Archives document costs one 304.
- **The parse lives on the Source Version, written once.** The ledger parses in the same transaction that creates the version (`html-text-v1`, archived under `archive://parsed/…`). A recorded parse is never overwritten (trigger). Re-parsing under a later parser version will need a separate `source_parse` record; that is deferred until a second parser version exists (the other open point).
- **Parser rules (`html-text-v1`)** are documented in `backend/atlas/parsing.py`. The content hash of each recorded fixture is pinned in `tests/fixtures/parser/golden.json`, so a change in output without a version bump fails the tests.
- **Clocks for SEC material:** `available_at` = `acceptanceDateTime` (basis `sec_acceptance`); `published_at` and `event_at` stay null (EDGAR's release time is the acceptance time, and the filing and report dates go in `metadata`); `first_seen_at` is the adapter's discovery time; `fetched_at` is the fetch; `ingested_at` is the database commit time. companyfacts has no acceptance time, so it uses `observed_discovery`.
- **Company IDs are deterministic** (UUIDv5 of the CIK, else the slug), and `company` has a `slug` column (the config key). Seeding is an idempotent upsert that audits only real changes. Coherent's CIK `0000820318` was verified with one SEC request (`data.sec.gov/submissions/CIK0000820318.json`: "COHERENT CORP.", COHR on NYSE, formerly II-VI INC). Its security is a TODO in the config: the listing start date isn't taken from a primary source yet.
- **Primary keys are named `id`,** following tickets 03 and 04, rather than the data model's `<table>_id`. Foreign keys keep `<table>_id`.
- **Raw content is served as an untrusted download:** `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox; default-src 'none'`, with the stored media type and no added charset. SEC HTML is never rendered on the application's origin (spec story 36). Parsed text is `text/plain; charset=utf-8` under the same headers.
- **An ingest job with fetch failures fails after recording everything else.** Its error lists each failed URL (spec story 22), and the retry is cheap because unchanged documents answer 304 or match by hash. Discovery failures (the submissions index) fail the attempt at once.
- **API additions beyond the spec's list:** `GET /api/v1/companies/{id}/sources` (the viewer's document list, story 46) and `GET /api/v1/sources/{id}`. Lists are paginated with `limit` (1–500, default 50) and `offset`, returning `{items, total, limit, offset}`.

## 2026-09-29: Assertions and review (ticket 08)

- **Review transitions (§5.4 lists the states, not the transitions).** `unreviewed`, `corroborated` and `disputed` are open: each may move to any other state except back to `unreviewed`. `rejected` and `superseded` are final. Repeating the current state isn't a transition (409 `invalid_transition`). Both the service and a database trigger (migration `0006`) enforce this.
- **Supersession is a review.** `POST /assertions/{id}/review` with `{"review_state": "superseded", "superseded_by": <successor>}`. The successor must exist, must differ, and must not itself be rejected or superseded, so supersession chains can't form cycles. `superseded_by` is set exactly when the state is `superseded`. Only the review columns ever change; the statement is immutable (trigger), and a correction is the successor Assertion.
- **The quote binding is exact.** `parsed_text[span_start:span_end] == quote`, with offsets in characters (Unicode code points) of the archived parse, which the API serves as UTF-8. There's no case or whitespace folding, and no searching. A refusal says where the quote does occur, if anywhere. The viewer (ticket 10) must convert from JavaScript's UTF-16 indices. `page_or_anchor` is a free label for now: `html-text-v1` defines no section anchors, so the offsets are the binding. (From `text-v2`, an Assertion on a PDF version that gives no label gets its page's, from the version's page anchors; see "PDF parsing and language".) Only versions whose parse is `parsed` or `incomplete` can be quoted.
- **The API calls `verification_status` `review_state`** (as `docs/data-model.md` planned). A company's Assertions are those that name it as subject **or** object. The list also filters by `source_version_id`, for the viewer. It's ordered oldest first.
- **Mutation responses** are `{assertion, audit_event_id}` (spec: "audit IDs on mutations"). Refusals use the error envelope: 422 (`quote_mismatch`, `no_parsed_text`, `unknown_company`, `unknown_source_version`, `invalid_successor`), 409 (`invalid_transition`) and 404 (`not_found`). FastAPI's request validation errors now use the same envelope app-wide (code `invalid_request`).
- **The reviewer is the configured actor** (`reviewer_id` holds the actor name, as `created_by` does), until an authenticated principal exists.
## 2026-09-29: retention into memory (build ticket 13)

- **Sections (`sec-items-v1`, `atlas.retention.sections`):** an SEC filing's primary document (10-K, 10-Q, 8-K and amendments) is split on its Item headings, qualified by `PART` (`part-ii-item-1a`; 8-Ks give `item-2-02`). The body starts at the last occurrence of the first heading's (part, item), which skips the table of contents; the text before it is the `cover` section. Everything else (exhibits, press releases) is cut into chunks of at most 12,000 characters at line breaks. Offsets are character indices into the parsed text, and a version's sections tile it. Items aren't split further: a 140k-character Risk Factors section is one Hindsight document, and Hindsight chunks it internally.
- **The cover is retained too**, although it may yield few facts, so no text of a filing is silently left out of memory.
- **Tags:** `company:<uuid>`, `theme:<slug>` for each configured theme containing the company, `source:<provider>` (`sec_edgar`), `doctype:<source_type>` (`filing`) and `form:<form_type>` (an exhibit carries its filing's form). **Metadata** is `source_version_id`, `section_anchor`, `char_start`, `char_end` and `available_at` (strings: the gateway's metadata is `dict[str, str]`). The timestamp is `available_at`; the context is the document title plus the section heading.
- **Link, don't re-retain:** a Source Version whose raw SHA-256 matches a version already retained in the bank (any of its sections not `failed`) gets one `linked` row per section of that version, pointing at it, and no Hindsight call. The decision takes an advisory lock on the raw hash, so two identical versions can't both retain. The linked copy's own tags (for example a different company) are not in memory; the retained twin's are.
- **Retain needs an applied bank template:** the retain job fails, naming `atlas hindsight apply-template`, when the bank has none, since the template version is recorded on every memory document.
- **Polling:** a `poll_operation` job waits for a terminal status with the gateway's `wait_for_operation` (`ATLAS_RETAIN_POLL_TIMEOUT_SECONDS`, default 240 s, below the 300 s lease; interval 5 s). A timeout fails the attempt with the last status recorded on the operation, and it is retried up to `ATLAS_RETAIN_POLL_ATTEMPTS` (5). A job queue backoff and pause are ticket 14.
- **Zero facts:** after completion each section's `memory_unit_count` (`GET …/documents/{id}`) is its fact count. A zero-fact section gets a `reprocess` job, which re-retains all such sections of that operation as one batch under the same document IDs (reprocess count 1); if it is still zero after that operation, it is `zero_fact`. The documents `reprocess` route exists in 0.10.1 but no interaction with it is recorded, so it isn't used. A document missing after a completed operation is `failed`.
- **Failures stay visible:** a `failed`, `cancelled` or `not_found` operation marks its pending sections `failed` with Hindsight's error (or "Hindsight reported the operation failed with no error message"); the operation row keeps the status, error, retry count and result metadata. Failed sections are not retried automatically.
- **No run record for retains yet.** Retains don't start a `run` (it needs LiteLLM configured, and tokens only arrive per operation as `result_metadata.total_tokens`, which is stored). Memory documents carry the template version.

## 2026-09-29: queue pause and pacing (build ticket 14)

- **What pauses the queue.** A job attempt fails with a *quota* or *availability* error, and the job's kind is **pausable**. Pausable kinds are those that depend on Hindsight and, through it, LiteLLM: `retain`, `poll_operation` and `reprocess`, with `reflect` and `refresh_mental_model` to join when they exist. A kind is marked pausable where it's registered (`HandlerRegistry.register(..., pausable=True)`). Classification (`atlas.jobs.pacing`):
  - `quota`: HTTP 429 from Hindsight or LiteLLM, or a failed operation whose error (or a sub-batch's error) mentions 429, a rate limit, too many requests, or insufficient quota or balance. The MiniMax cap-out reaches Hindsight as a 429 from LiteLLM.
  - `unavailable`: HTTP 502/503/504, a connection failure to Hindsight or LiteLLM, or an operation error naming 502–504, "service unavailable", a refused or reset connection, `APIConnectionError` or "overloaded".
  - Anything else is ordinary. A Hindsight 5xx is classified by its body. An arbitrary exception's text is never matched, so an unrelated error that happens to mention "429" doesn't pause. Operation timeouts aren't classified, because a stuck operation can be the document's fault.
- **Pause representation (data model §3.5, resolved):** a single-row `queue_pause` table, not a derived view. It holds the level, class, reason, paused kinds, backoff, `paused_at`, `resume_after`, the episode start, the job that caused it and `cleared_at`. There's also an append-only `queue_pause_event` history, one row per pause entered. A view over jobs and operations couldn't express a backoff level that resets on success.
- **Backoff:** 60 s × 2^(level−1), capped at 1 h. The level counts the pauses entered since the last success of a pausable job. A failure while a pause is in force doesn't lengthen it, because another in-flight job hitting the same 429 would otherwise escalate the level. `ATLAS_QUEUE_PAUSE_BASE_SECONDS` defaults to 60 and `ATLAS_QUEUE_PAUSE_MAX_SECONDS` to 3600; neither may exceed 3600.
- **Pause behaviour:**
  - While paused, the pausable kinds aren't claimed. Other kinds, such as `ingest` (SEC fetching), keep running.
  - The job that hit the failure goes back to the queue **without using up an attempt**, and the failure is recorded with its classification, so quota never fails a job.
  - The pause lifts by itself at `resume_after`. The first pausable success after that resets the level (`cleared_at`).
- **A failed operation with a quota or outage error** is recorded with `error_class`, and its sections stay `pending` instead of `failed`. Its poll job raises `TransientFailure`, which pauses the queue. After the pause, the poll job's next attempt **resubmits the same sections** as a new batch under the same document IDs; Hindsight gives it a new operation. A reprocess isn't counted twice. The new operation keeps the original submitting job, so a follow-up reprocess inherits its class. A `permanent` failure behaves as before (ticket 13).
- **No model switching, ever.** Atlas never changes the alias, the Hindsight LLM config or the route. Pausing is the only response to quota or an outage.
- **Backfill class.** Backfill is a per-job class (`job.job_class`, `interactive` by default), not a set of kinds. A job is marked as backfill when enqueued: `atlas ingest --backfill` or `atlas jobs enqueue ... --backfill`. Class is inherited like this:
  - A backfill ingest's `retain` jobs are backfill.
  - A `reprocess` takes the class of the job that submitted the operation.
  - `poll_operation` is always interactive, because polling spends no quota and a submitted batch shouldn't wait a day to be observed.

  Every backfill-class job, of any kind, is claimed only inside the window. Deciding by class rather than kind keeps "the owner's own ingest runs now" and "the three-year backfill waits for the night" as two uses of the same kinds.
- **Window:** `ATLAS_BACKFILL_WINDOW` is `HH:MM-HH:MM` in local time in `ATLAS_BACKFILL_TIMEZONE`. The defaults are `01:00-07:00` and `UTC` (**changed by ticket 27:** the window is now empty by default and may list several ranges; see "Quota-window pacing"); the owner sets their zone (for example `Europe/Stockholm`). The start is inclusive and the end exclusive, a window may wrap past midnight, and an empty value means no window. A backfill job that's running when the window closes finishes; only claiming is gated.
- **Clocks:** pacing (the pause and the window) reads the application clock, which is injectable (`JobQueue(clock=...)`, `create_app(clock=...)`), so tests control it. Leases stay on the database clock.
- **`GET /api/v1/queue`** returns the pause (paused now, level, class, reason, kinds, backoff, paused at, resume after, the episode start, cleared at, total pauses), the backfill window (open now, next opening) and pending jobs by kind (queued, running, backfill queued, paused).
- **Metrics are read from the database at scrape time** on the API's registry (`atlas.metrics.StateCollector`), because the worker has no HTTP server. The metrics are:
  - `atlas_queue_paused`, `_pause_level`, `_pause_backoff_seconds`, `_pause_duration_seconds` and `atlas_queue_pauses_total{error_class}`
  - `atlas_queue_jobs{kind,job_class,status}` (queue depth) and `atlas_jobs_failed_total{kind}`
  - `atlas_hindsight_operations_total{kind,status,error_class}`
  - `atlas_retained_sections_total{outcome}` and `atlas_memory_sections_pending`
  - `atlas_zero_fact_sections_total`
  - `atlas_state_metrics_up`

  Counters count rows in terminal states. The pause duration counts only while jobs of a paused kind are queued, so an idle queue after an outage doesn't alert.
- **Alert rules:** `configs/prometheus/atlas-alerts.yaml`, a PrometheusRule for home-ops (not deployed from here). It alerts on:
  - ≥ 3 permanent operation failures of a kind in 1 h
  - ≥ 3 failed jobs of a kind in 1 h
  - ≥ 5 zero-fact sections in 6 h
  - a pause holding back work for over 2 h
  - the metrics database being unreadable
## 2026-09-29: recall and reflect with resolved citations (build ticket 15)

- **Quote normalization rule (`whitespace-and-typographic-quotes-v1`, `atlas.research.quotes`).** A quote in an answer counts only if it occurs in the archived parsed text of a section the answer's resolved citations lead to, after normalizing exactly two things on both sides: typographic quotes (‘ ’ ‚ ‛ → `'`, “ ” „ ‟ → `"`) and whitespace (each run of `str.isspace` characters, including newlines and no-break spaces, → one space; the quote's ends trimmed). Case, punctuation, dashes, ellipses and digits must match. Quotes are the answer's double-quoted passages (`"…"` or `“…”`, on one line); single quotes are apostrophes too, so they aren't quotation marks. A matched quote is reported as the code-point span of the original parsed text, like an Assertion's offsets, and each answer records the rule's name.
- **Citation states.** *resolved*: every hop reached a Source Version section (observation → `source_memory_ids` → world fact → `document_id` `srcv:<uuid>:<anchor>` → the `memory_document` row, whose Source Version and anchor must equal the fact's `metadata.source_version_id` and `metadata.section_anchor`), and a quote matched in one. *unverified*: content with no memory ID (a raw chunk), a document that isn't an Atlas section or isn't in the ledger, metadata that disagrees with the ledger, an observation with no sources, more than 3 observation hops, or a quote that matches no cited section. *broken*: the cited memory, or any source memory of a cited observation, answers 404. An observation takes its worst hop's state. Only resolved citations carry sources, and only they are presented as `evidence` (grouped by section, with their matched quotes). A verbatim quote in a chunk-only answer stays unverified, because nothing resolved leads to a section to check it against.
- **Memory text is never a quote.** Hindsight rewrites facts (`… | When: … | Involving: …`), so a memory's text is shown as Memory and never validated as a quotation; only the answer's quotes are.
- **Scope.** `company_ids` (company UUIDs) and `theme_ids` (theme slugs from the universe config) become the retain tags `company:<uuid>` and `theme:<slug>`, matched `any_strict`: a union that excludes untagged memories. There is no intersection of companies and themes, because one strict mode applies to all tags; and a memory is tagged with every theme its company belongs to anyway. Unknown companies or themes are refused (422) before any Hindsight call.
- **Recall is synchronous and not stored**; each memory carries its provenance, and the response lists the Evidence behind the resolved ones. **Reflect is a job:** `POST /memory/reflect` records a `pending` research answer (audited `research_answer.requested`) and enqueues `reflect` (idempotency key `reflect:<answer id>`); the job asks Hindsight with `include.facts`, resolves, and stores (`research_answer.answered`). On its last failed attempt it marks the answer `failed` with the error (`research_answer.failed`).
- **Structured output is checked by Atlas too.** A response schema must be a valid JSON Schema (`jsonschema`, now a runtime dependency) with `"type": "object"` and no union types (422 `invalid_response_schema`, before anything is recorded). The stored `structured_output_error` is Hindsight's own error, "no structured output", or the first schema validation failure; the output is kept as returned either way.
- **Runs.** A reflect job starts a `run` (kind `reflect`) when Hindsight and LiteLLM are both configured, and finishes it with the reflect's input/output tokens; otherwise the answer's `run_id` is null.

## 2026-09-29: code review fix-up (spec axis)

- **Revised versions are available from when Atlas observed them (reversible; tightens Part A stories 29 and 31).** A document's first Source Version keeps `available_at` = the filing's `acceptanceDateTime` (basis `sec_acceptance`). A version that **supersedes** an earlier one (its content changed) takes `available_at` = its own `fetched_at`, basis `observed_revision` (migration `0011` adds the value). Reason: temporal integrity. The changed bytes weren't public at the original acceptance, so dating them there would let a later revision leak into an earlier point-in-time view, exactly the risk the spec lists in §16 as "delayed publication masquerades as early knowledge". The fetch time is conservative (the change happened at or before it) and never overstates availability. The original acceptance stays in the version's `metadata.acceptance_datetime`. Reversible: if EDGAR ever gives a reliable per-revision timestamp, a new basis can use it for later versions; existing rows are immutable and keep theirs.
- **What the audit trail covers in the job queue.** Part A says every mutating service writes an event in the same transaction as its change. For the queue that means: a **new job** (`job.enqueued`, not a repeat enqueue of an existing key) and the **queue pause entered and cleared** (`queue.paused`, `queue.pause_cleared`, entity `queue_pause`). ## 2026-09-29: EDGAR dissemination time (Phase 3-6a ticket 10)

- **`available_at` for EDGAR filings is when EDGAR disseminated them, not acceptance (tightens the ticket-07 clock rule and Part A story 29; spec §5 "conservatively", §9.1).** Given `acceptanceDateTime` (`atlas.sources.edgar_calendar.edgar_dissemination_time`, `atlas.sources.edgar.filing_availability`):
  - accepted on an EDGAR business day between 06:00 and 17:30 ET inclusive: `available_at` = acceptance;
  - otherwise (after 17:30, before 06:00, on a weekend or a closure day): 06:00 ET on the next business day. Eastern time is America/New_York, so the opening is 06:00 EST or EDT as that day requires (the `tzdata` package is now a runtime dependency, so the slim image doesn't depend on a system zone database);
  - ownership and similar forms (3, 4, 5, 144, Schedules 13D/13G, the MEF forms, …) are disseminated until 22:00 ET instead. Only the forms the current manual lists: the old names `SC 13G` and `SC 13G/A` keep the 17:30 cutoff, because recorded indexes show them accepted after 17:30 in 2019–2023 with the next day's filing date (the late window came with the renamed Schedules).

  Sources (SEC primary):
  - [FM2] *EDGAR Filer Manual, Volume II* (v78, 14 September 2026), <https://www.sec.gov/files/edgar/filermanual/edgarfm-vol2-v78.pdf>. §2.3.1: "EDGAR is available for filings … each business day, Monday through Friday, from 6:00 A.M. to 10:00 P.M., Eastern Time." §3.2: "Normally filings received after 5:30 P.M. Eastern time will receive a filing date of the next business day and will not be disseminated until the next business day", and the list of forms "disseminated until 10:00 P.M." §2.1.3: once accepted, "Dissemination can often occur within seconds of your transmission." Payments section: "Monday through Friday except federal holidays".
  - [Hours] *Accessing EDGAR Data*, <https://www.sec.gov/search-filings/edgar-search-assistance/accessing-edgar-data>: filings submitted after 5:30 p.m. ET appear in the next business day's index.
  - [Cal] *EDGAR Calendar*, <https://www.sec.gov/submit-filings/filer-support-resources/edgar-calendar>: "The EDGAR system will not receive, process, or accept filings in observance of the following federal holidays", listing 2026's eleven dates.
  - [Closures] SEC announcements of extra closures: 24–26 December 2025 (<https://www.sec.gov/newsroom/whats-new/edgar-will-be-closed-december-24-2025-through-december-26-2025>); by title in SEC's newsroom, 24 December 2024, 9 January 2025 (President Carter), 24 December 2019, 24 and 31 December 2021; and that EDGAR "Will Operate Normally on Inauguration Day" (20 January 2021).

  The opening is taken as the dissemination time of a held filing: [FM2] says only "the next business day", and EDGAR can disseminate nothing before it opens, so 06:00 ET is the earliest such a filing can have been public. **Checked against 8,366 real filings** (distinct accessions in the submissions indexes of 15 filers recorded during the Phase 3-6a research, accepted 2019–2026; 2,092 of them 10-K, 10-Q, 8-K, 20-F or 6-K): the rule never puts a filing on an earlier date than EDGAR's own `filingDate`. It puts 59 later, all conservative: 36 SEC-generated or correspondence submissions (EFFECT, CORRESP, UPLOAD), 8 old-style Schedule 13G amendments, 8 other registration and plan forms, and 7 target-form filings accepted minutes to hours after 17:30 that EDGAR still dated that day (received before 17:30, or a filing-date adjustment; e.g. three 2020-06-29 8-Ks at 21:29–21:37 ET). Using `filingDate` to rescue those would trust an adjustable date over the rule; not done.

- **The holiday table is explicit, in code, with a hard range.** `EDGAR_HOLIDAYS` in `backend/atlas/sources/edgar_calendar.py` lists every closure weekday from 2019-01-01 to 2027-12-31: the federal holidays of 5 U.S.C. 6103 with their weekend observance (2026 matches [Cal] exactly), plus the announced extra closures above. **2027 is statutory only**, since SEC hasn't published its 2027 calendar; when it does, check it and add any closures. **Outside the range, `EdgarCalendarRangeError` is raised; nothing is guessed.** Ingest of a filing outside the range therefore fails visibly (its job fails with the message naming the table to extend), and the correction command reports and logs such versions and leaves them as recorded. Extending the table before 2027-12-31 is a maintenance task (the error names the file).

- **Basis `sec_dissemination` only when it differs from acceptance.** A filing disseminated at acceptance keeps basis `sec_acceptance`; one EDGAR held gets `sec_dissemination` (migration `0012` adds the value). Why not always `sec_dissemination`: then every in-window version recorded before this rule (all `sec_acceptance`, all already correct) would need a correction to mean the same thing as a new one. With this choice, `sec_acceptance` means "public at acceptance, which was inside the window" for old and new rows alike once the held ones are corrected, and the basis itself tells a reader which filings EDGAR held. `acceptanceDateTime` stays in `metadata.acceptance_datetime` either way.

- **XBRL facts take their filing's availability.** Research ticket 04 already settled that a fact's `available_at` is its filing's, never the companyfacts fetch. `filing_availability(filing)` is that one rule for a filing's documents and its facts. Phase 5 normalization resolves each fact's `accn` to its `SecFiling` and calls it (so ticket 04's `sec_filing_date` basis isn't needed). The companyfacts Source Version itself keeps `observed_discovery`.

- **Existing Source Versions: a recorded, append-only correction, never an edit (reversible).** Versions ingested before this rule with basis `sec_acceptance` but accepted after hours (every recent Lumentum 10-Q) are wrong, and their rows are immutable. `atlas ledger correct-availability` appends one row per such version to `source_version_availability_correction` (migration `0012`: the corrected `available_at`, basis `sec_dissemination`, a reason, `recorded_at`), in the same transaction as an audit event `source_version.availability_corrected` (old/new hashes of the availability). The table is append-only by ENABLE ALWAYS triggers, allows at most one correction per version, and a trigger rejects a correction that isn't **later** than the recorded value (a correction can only make availability more conservative). The command is idempotent; run it once after deploying `0012` (ingests after the deploy record the right value directly).
  - Every reader takes availability from the view `source_version_availability`: the correction if there is one, else the version's own. That means the API (`available_at`, `available_at_basis`, plus `recorded_available_at` / `recorded_available_at_basis`, what the version itself holds), citations and evidence, retention's `--since` window and retain timestamps. The version page shows a corrected value with the recorded one beside it.
  - Why not correct at read time from metadata: every as-of filter is SQL, so the calendar would have to be re-implemented in SQL or every reader would have to post-filter in Python, and a later change to the table would silently move old versions. A recorded, audited row makes the change a dated fact.
  - Already-retained memories keep the timestamp Hindsight was given at retain time; Atlas's own as-of reads use the corrected value.

## 2026-09-29: Role calls (Phase 3-6a ticket 07)

- **One way for every research role to call the LLM** (`atlas.roles`; spec Phase 4 "Roles", §7.2, §7.5). `POST /chat/completions` on LiteLLM with the `atlas` key; model `ATLAS_LLM_ROLE_MODEL` (default `MiniMax-M3`, by name, as the 2026-09-29 key entry decided for the aliases); extra body `ATLAS_LLM_ROLE_EXTRA_BODY` merged into the request (default `{"thinking": {"type": "disabled"}}`, the same switch Hindsight uses); `response_format` a strict `json_schema` named after the role; `metadata` `{run_id, role}`. The extra body can't override those fixed fields.
- **Directives in code, prompts in the repo.** The system message is the fixed `DIRECTIVES` (`atlas/roles/contract.py`) plus the role's prompt file `atlas/roles/prompts/<name>.v<N>.md`; each call records the prompt's name, version and the SHA-256 of its bytes (for the Research Snapshot's "prompts"). The user message is a JSON object `{"request": ..., "retrieved_data": [{id, source, text, trust: "low"}]}`: retrieved text is always a JSON string value under `retrieved_data`, which the directives call untrusted data, and never enters the system message. JSON quoting, rather than a delimiter tag, means no retrieved text can close its quote.
- **Strict schemas only.** A role's response model must compile to a schema LiteLLM/the provider can enforce strictly: every object `additionalProperties: false` and every property required (optional values are `X | None`). A role that breaks this fails when it is defined (`NotStrict`), not at call time.
- **Validation, one repair, then quarantine.** Before validating, a leading `<think>…</think>` block and a surrounding code fence are stripped (the dev probe needed both for MiniMax). A failed validation asks once more in the same conversation (the bad answer as the assistant turn, then the fixed `REPAIR_DIRECTIVE` with Pydantic's errors: type, location and message, never the input). A second failure quarantines the call: `role_call.status = quarantined`, `output` stays null, both answers and their errors stay visible (`GET /api/v1/runs/{id}/role-calls`), and `RoleOutputQuarantined` is raised, so the output can't be used.
- **Usage and the per-run budget.** Every completion LiteLLM answers is an `llm_call` row: `usage.prompt_tokens`/`completion_tokens`, the response's `model` and the `x-litellm-model-id` deployment hash (the routed model; runs still record `/model/info` routes for their aliases). A run's usage is the sum over its rows. `ATLAS_RUN_TOKEN_BUDGET` (default 200,000 input + output tokens; spec §7.4's "token ceiling", a starting value, not measured) is checked **before** each completion: at or over it, `TokenBudgetExhausted` (with `spent` and `budget`) is raised and nothing is sent, including a pending repair. Each request's `max_tokens` is the smaller of the role's cap and the budget left, so a run can overshoot only by one prompt. Parallel roles in one run (Skeptic ∥ Financial Analyst) can each pass the check at once; the key's `maxBudget` is the backstop, as the spec says. The `run` row's own `tokens_in`/`tokens_out` are still set by whoever finishes the run (the orchestration ticket, from `run_usage`).
- **Failures.** HTTP 429, LiteLLM's `budget_exceeded` error type (the key's maxBudget; it resets, so it is treated as quota), HTTP 502–504, a 5xx whose message names a quota or outage, and a connection failure raise `TransientFailure`, so a pausable job kind pauses the queue and requeues the job (the existing pacing rules). Anything else (400, 401, an unexpected response body, an unknown or finished run) is `RoleCallFailed`, an ordinary failed attempt. The `budget_exceeded` type is from LiteLLM's documentation of key budgets; like the rest of the chat fake, it has not been checked against a live response.
## 2026-09-29: PDF parsing and language (Phase 3-6a ticket 03)

- **The PDF library is pypdf, pinned exactly (`pypdf==6.19.0`).** Requirements: deterministic text extraction, a permissive licence, a pure-Python wheel (the image is slim and non-root; no compiler or system library), and maintained. pypdf is BSD-3-Clause, ships only a `py3-none-any` wheel with no required dependencies on Python 3.12, and has frequent releases (6.19.0, 16 September 2026). Considered: pdfminer.six (MIT, pure Python, good layout analysis, but slower and its layout heuristics add tunables that would become part of the parser version); pypdfium2 and PyMuPDF (binary wheels; PyMuPDF is AGPL); pdfplumber (built on pdfminer.six). Its exact pin is part of the parser: extraction can change between releases, so **upgrading pypdf is a new parser version**, checked by the pinned hash in `tests/unit/test_pdf_parsing.py`. Encrypted PDFs that need the optional `cryptography` extra fail to parse (`failed`, with the error); none of the pilot's sources is known to encrypt.
- **Parser version `text-v2`** (was `html-text-v1`). It keeps v1's HTML and text rules exactly (same text, same content hash: `tests/fixtures/parser/golden.json` pins both versions to the same hashes), and adds PDF text, page anchors and the language. So Source Versions parsed under `html-text-v1` need no re-parse, and the `source_parse` table the data model anticipates for re-parses is still unneeded. The rules are in `atlas.parsing`'s docstring.
- **PDF text and page anchors.** Each page's text is pypdf's plain-mode `extract_text()`, C0 controls removed, then v1's normalization and line rules; the document's text is its pages' texts in order. `source_version.page_anchors` records, per page, `{page, label, start, end}`: the 1-based page number, its label from the PDF's `/PageLabels` (so an annual report's printed "page 12" is findable; else the number), and its code-point range in the parsed text, the same offsets Assertions use. Anchors are offsets beside the text, never markers inside it, so quotes and hashes stay plain text. An Assertion on a PDF version that gives no `page_or_anchor` gets its page's label ("page 1 (PDF page 2)", or "pages i–1 (…)" across pages); the offsets stay the binding. The viewer lists the anchors and jumps to each page.
- **Image-only PDFs are `unsupported`.** A PDF none of whose pages yields text (a scan without OCR) gets `parse_status=unsupported`, with the reason in `parse_error` (now set iff `failed` or `unsupported`), and no parsed text, so it can't be quoted or retained. Atlas does no OCR: OCR output isn't deterministic across engine versions and isn't a verbatim span of the source. A PDF with text on some pages only parses normally; its empty pages have empty anchors.
- **Language.** `source_version.language` is a lowercase ISO 639 primary subtag, or `und`. In order: the adapter's declaration (`SourceCandidate.language`; EDGAR declares `en` for every candidate, since Regulation S-T Rule 306 requires filings in English; an exchange adapter declares what the exchange lists), else the language the document declares (`<html lang>`, a PDF catalog's `/Lang`), else a deterministic guess from the parsed text (Han/kana/Hangul share, then counts of function words for `en`, `fr`, `de`, `es`, `it`, `nl`; too few or a near tie is `und`). No language-detection library: the common ones are statistical (langdetect is randomized unless seeded) or large, and a guess only matters when neither the source nor the document says. Versions before migration `0014` are all EDGAR and get `en` (the column's default while it's added, then dropped: no UPDATE of immutable rows).
- **Only English is retained or extracted** (map: "extraction is English-only in the pilot"). `enqueue_retains` skips versions whose language isn't in `atlas.retention.service.RETAINABLE_LANGUAGES` (`en`), and a retain job for one records `not_retainable` with the language. `und` counts as not English: a document whose language can't be established isn't retained. Non-English versions are archived and viewable as usual. Later extraction (Investigator) must apply the same filter.
- **Fixtures are generated, not downloaded.** `scripts/make_pdf_fixtures.py` writes three small PDFs by hand (no PDF library, uncompressed streams, no timestamps or `/ID`), so the bytes are identical on every run; a unit test regenerates them and compares. They are synthetic, not any issuer's document.
- **Not yet exercised by an adapter.** No adapter fetches PDFs until the exchange adapters (tickets 04–06); the tests record the fixtures through `SourceLedger.record` as an adapter's fetch would, under the SEC provider (the only one `describe` knows).
## 2026-09-29: Evidence Families (Phase 3-6a build ticket 11)

- **Rule** (`atlas.ledger.families`; map ticket 05): a parsed Source Version joins the family of a member with the same `content_sha256` (exact), else of the nearest member whose 64-bit SimHash is within that family's recorded `max_hamming_distance` (default 3, `ATLAS_EVIDENCE_FAMILY_MAX_HAMMING_DISTANCE`), else founds a family. Ties go to the earliest-assigned member. Unparsed versions have no family.
- **SimHash is self-implemented and fixed** (`simhash64-w3-blake2b-v1`): NFKC + casefold of the archived parse, tokens are runs of Unicode letters/digits, features are word 3-shingles weighted by occurrence, each hashed with unkeyed BLAKE2b-64 (big-endian). No dependency, and never Python's `hash()`, so a fingerprint is the same in every process. A change to any of this is a new rule name; families only take members computed by their own rule.
- **Append-only, never merged.** A version's family never changes; a version near two families joins the nearest. Single-link growth is bounded by that: a chain of drifting edits can still end in a second family, which errs toward counting two witnesses where there may be one. Raising a family's threshold later needs a new rule or a re-assignment design; not built.
- **Assignment is serialized** by a transaction-scoped advisory lock (`atlas.evidence_family`), taken before the audit chain's lock, so concurrent copies can't found two families. The near-duplicate search is a scan with `bit_count` over all members (Postgres 14+); fine at today's scale, an index (e.g. banded SimHash) when the ledger reaches hundreds of thousands of parsed versions.
- **Checked on the fixtures:** the recorded Lumentum and Coherent filings are 25–39 bits apart pairwise (no false family); the synthetic wire-service copy of the Q4 FY2026 release is 2 bits from the recorded one. Near-identical templates (8-K cover pages of different filings) are untested: the fixtures hold one 8-K cover. Press-release 8-Ks drop the cover by default (exhibits only); if other covers group falsely in production, the threshold (or a minimum token count) is the lever.
## 2026-09-29: XBRL normalization (Phases 3–6a build ticket 18)

Rules from the research note `docs/research/xbrl-normalization.md` (branch `research/xbrl-normalization`, `bc25fa6`) and the resolved map ticket 04, implemented in `atlas.financials` (migration `0017`).

- **A fact's `available_at` is its filing's, via `filing_availability`.** The `ingest` job normalizes the company's companyfacts Source Version after recording it (once per version and normalizer version), mapping each fact's `accn` to its `SecFiling` in the submissions index that ingest fetched (a conditional re-request). A fact of a held filing gets `sec_dissemination`; `accepted_at` records `acceptanceDateTime`.
- **Fallback when acceptance is unknown: 23:59:59 ET on the fact's `filed` date, basis `sec_filing_date_eod`.** It applies when the accession isn't in `filings.recent` (older pages aren't followed; the fixtures are trimmed) or its acceptance lies outside the EDGAR holiday table (`EdgarCalendarRangeError`, e.g. Lumentum's 2015–2018 filings). EDGAR's filing date is the day it disseminated the filing (a filing accepted after 17:30 gets the next business day's date), so the end of that day is never earlier than the filing was public by EDGAR's own dating. This differs from ticket 10's choice for filing Source Versions, whose ingest fails outside the table: a companyfacts document carries a filer's whole history, and one pre-2019 fact must not block the rest. Conservative, reversible: a later normalizer version with fuller submissions data can record exact times.
- **As-of selection per (taxonomy, concept, unit, start, end):** the observation of a periodic report (10-K, 10-Q, 20-F, 40-F and their amendments) with the greatest (`available_at`, `accepted_at`, accession) at or before the cutoff. `fy`, `fp` and `frame` are stored for information only; `frame` (SEC's "latest filing" marker, computed now) would leak the future.
- **Restatements are linked, never overwritten.** Each observation stores its predecessor in filing order and `restates` (different value) or `reaffirms` (same value). A restatement is **suspect** (still selected, flagged for review) on a sign change, a change over 50%, or a period ending more than two years before the filing's report date (the submissions `reportDate`, else the latest non-`dei` period end among the accession's facts). Lumentum's EPS mis-tag (3.29) trips the size and age tests; its 10-K/A correction back to 0 is flagged too (a 100% change), which a reviewer sees as the pair. Known limit: linkage is computed when an observation is inserted, so a later-inserted observation that sorts *before* stored ones doesn't relink them (rows are immutable); companyfacts carries full history, so this only happens if SEC backfills an older filing's facts.
- **A value changed inside companyfacts** for the same accession and key is a new observation, available from the companyfacts version's own availability (basis `observed_revision`), restating the earlier one.
- **Metrics are concept families with precedence, in versioned config** (`configs/financials/metrics.yaml`). For each (unit, period) the value comes from the latest filing that tagged any family concept; within that filing the first listed concept wins, and a different value under another listed concept flags `concept_mismatch`. Debt tags are never summed (`ShortTermBorrowings` duplicates `LongTermDebtCurrent` for Lumentum); the research note's composite total-debt rule is not implemented: `total_debt` is only `DebtLongtermAndShorttermCombinedAmount` / `Borrowings` when tagged.
- **Derived quarters are computed when read, not stored:** for a flow metric in a plain currency unit, adjacent year-to-date values with the same start give the quarter between them (Q2 = H1 − Q1, Q3 = 9M − H1, Q4 = FY − 9M) when the difference is 84–98 days and no reported value exists for it. So 52/53-week calendars work (98-day quarters, 371-day years), a derived value always reflects the as-of inputs, and it lists both source observations with `available_at` = the later one. Share counts, weighted averages and per-share values are never derived.
- **No currency mixing.** Units are part of the key; values stay as filed (`fx_basis` null; `currency` from the unit). A derivation across units raises `CurrencyMismatch`. The `fx_basis` column requires a rate source, rate date and source currency if it is ever set; there is no FX source yet (the research note's convention, period-average for flows and period-end for instants, is recorded for when one is licensed).
- **Not done here:** strict replay (research §4.1: also require the companyfacts Source Version's `ingested_at <= as_of`) belongs to Phase 6a replay; the observations keep `source_version_id` for it.

## 2026-09-29: Investigator Claims → Assertions (Phase 3-6a ticket 10)

- **The Investigator is a role on the role-call foundation** (`atlas/roles/investigator.py`, prompt `investigator.v1.md`), run by the `extract_claims` job (`atlas.claims`) over the Source Versions its payload names (`{"source_version_ids": [...], "question"?, "run_id"?}`; at most 25, the spec's per-run document bound). The job starts its own run (`kind = claim_extraction`) unless given an unfinished `run_id` (for ticket 14's investigations, which then finish the run themselves).
- **Passages, not whole sections.** Each Source Version is split by the retention sectioner (`sec-items-v1`), so a passage's section is a memory document's section; sections are cut into windows of at most 3,000 characters at line breaks. A window is sent when it names a known company other than the document's own (**entity tag**: display or legal name, or the legal name without corporate suffixes, case-sensitive and whole-word, so "coherent optics" never tags Coherent) or when a recall for the job's `question`, scoped by `company:` tags to the documents' companies, resolves to its section (**recall hit**). Entity-tagged windows first, then recall-only ones; at most `ATLAS_INVESTIGATOR_MAX_PASSAGES` (24), `ATLAS_INVESTIGATOR_PASSAGES_PER_CALL` (6) per call. Both are starting values, not measured.
- **A Claim names a passage and offsets in it.** The model answers `passage_id`, `quote`, `quote_start`, `quote_end` (code points into the passage's text); Atlas adds the passage's start to get the Source Version span (the spec's "`source_version_id`, char offsets"). The span is then checked by **the existing Assertion span check** (`check_quote`): exact text at exact offsets, no search. A Claim whose quote occurs elsewhere is rejected (`quote_mismatch`, the reason saying where it does occur), never moved. **Open risk:** models are poor at counting characters, so live runs may reject many true quotes on offsets alone; the live suite should measure it before deciding whether to let Atlas locate a quote that occurs exactly once in its passage. *(Measured and decided: see "Claim quotes are located, not trusted" below; the no-search rule is superseded.)*
- **Checks, in order** (the first failure is the rejection reason): whitelisted predicate; known layer; passage sent in that call; known subject, known company object or named product object, subject ≠ object; offsets inside the passage; the span check; the quote names both parties (a company by name, or the document's own company as "we"/"our"/"the Company"); the quote uses directional language for its predicate (`no_directional_language`). Rejected Claims are `claim` rows with `outcome = rejected`, a `reason_code` and a message, visible at `GET /api/v1/claims` and counted in `atlas_claims_rejected_total{reason}`.
- **The whitelist and direction.** Build plan §5.5's nine predicates, each with a stated direction (`supplies`: the object is the subject's customer; `buys_from`: the object is the subject's supplier) and object kind (a company, or a product/material/technology in `object_text`). Nothing is ever inferred from a Claim: one accepted Claim is one Assertion with the proposed predicate. "Works with", "partners with" and "collaborates with" map to no predicate; the response schema leaves `predicate` a string so such a proposal is a rejected Claim with that reason rather than a failed call.
- **The layer taxonomy** as slugs: `substrate`, `epi`, `chip-laser`, `dsp`, `module`, `contract-manufacturing`, `system` (spec: substrate → epi → chip/laser → DSP → module → system, plus contract manufacturing). The same vocabulary as the universe config and the company table (`atlas.companies.Layer`).
- **Co-mention guard (the gate).** Two companies named in one sentence carry no relation: a quote must contain a predicate-specific directional cue (a conservative pattern list in `atlas/claims/predicates.py`), or the Claim is rejected and no Assertion is created. So every Assertion an extraction creates is Relationship-eligible, and a co-mention-only passage (the Coherent 10-K's peer group naming Lumentum) produces none, whatever the model claims. The cue proves only that directional language is present; whether its direction is right is the reviewer's job (ticket 12), which extends this list.
- **Resumable batches.** Progress is stored per batch with the passages, so a job requeued by an LLM quota or outage (`extract_claims` is pausable) resumes at its next batch in the same run. A quarantined answer is a batch with no Claims; a spent run budget ends the extraction `budget_exhausted` with what it found, and the job succeeds. Accepted Claims' Assertions are created inside the batch's transaction (`Assertions.create_within`), so a crash never leaves an Assertion without its Claim.
- **Epistemic types.** An Investigator Claim is `direct_source_statement`, `company_claim` or `third_party_report` (the response schema's enum); an agent's own inference is never a Claim.

## 2026-09-29: Relationships and review (Phase 3-6a ticket 12)

- **An edge is (subject, predicate, object, layer).** The object is a company, or for the product predicates the Assertion's `value_json.object_text` (compared casefolded, whitespace collapsed). The layer is part of the identity, so "Coherent supplies NVIDIA" at `chip-laser` and at `module` are two edges and a layer confusion shows up as its own edge. The product is not: an edge lists the products its Assertions name. `competes_with` is stored in the direction proposed (no merging of A–B with B–A).
- **The `review_relationships` job** machine-reviews Assertions (named in its payload, or a sweep of every open one with a whitelisted predicate and no review yet, oldest first, at most 100). It forms a Relationship only if its predicate is whitelisted, it is open (not rejected or superseded), `value_json.layer` is a known layer, its object is present and differs from the subject, **and its quote has directional language for the predicate**; otherwise it is recorded `not_eligible` with the reason and forms no edge. Patterns can't tell who "we" is, so they never judge the direction; that part of "explicitly directional language" is the Reviewer's classification. Anything else is `needs_human_review` (the exceptions queue) with reason codes.
- **The Reviewer is asked only about Assertions that pass the deterministic checks** (span, Tier A, unhedged): the others go to a human whatever it would say, so they cost no tokens (`reviewer_status = skipped`). It is a separate role (`roles/reviewer.py`, prompt `reviewer.v1.md`) with its own strict schema, called `ATLAS_REVIEWER_ASSERTIONS_PER_CALL` (5) Assertions at a time. Each item's quote and ±600 characters of context go as quoted low-trust `retrieved_data` (`<item>:quote`, `<item>:context`), never in the request. The role runs on the configured role model (MiniMax-M3); the map's "the Skeptic model" is read as "a separate call with its own prompt", not a separate model deployment.
- **Failures.** A quarantined answer or an item the answer leaves out sends that edge to humans (`reviewer_quarantined`, `reviewer_no_answer`). An LLM quota or outage pauses the queue (the kind is pausable); the retry keeps the job's run (`relationship_review_job`) and reviews only what is left. A spent token budget stops the job `budget_exhausted` and leaves the rest unreviewed for a later job (they are not sent to humans for a reason that isn't theirs).
- **Edge state.** A new edge takes its first review's outcome. Later Evidence is added (`relationship.evidence_added`); a passing witness lifts an exception to `machine_reviewed` (`relationship.machine_reviewed`), but a failing one never demotes a machine-reviewed edge (its reasons stay visible in `review_reasons`). **Machine review never changes an owner's decision.** The owner may approve or reject any edge in any state (`POST /relationships/{id}/review`, `{review_state: approved|rejected, note?}`); repeating the current decision is 409 `invalid_transition`. Every change is audited (`docs/data-model.md` §3.1e). Owner approval is what ticket 20's publish gate will require of the Relationships a Hypothesis depends on.
- **Counts.** `evidence_count` counts supporting Assertions not rejected or superseded; `family_count` the distinct Evidence Families of their Source Versions (a version in no family counts as its own), i.e. independent witnesses.
- **Not automatic after extraction.** `extract_claims` doesn't enqueue a review: an investigation's final stop chains one for its Assertions (ticket 16; in its own run, see below); by hand, `atlas jobs enqueue review_relationships --key K --payload '{}'`.
## 2026-09-29: Investigation orchestration (Phase 3-6a ticket 14)

- **The plan is fixed and visible from the start.** Round 1 is `scout` → one `investigator:<slug>` per seed company → `skeptic` ∥ `financial_analyst` → `editor`, stored as `investigation_task` rows (spec "task rows per role") with their dependencies and premises. The Skeptic and Financial Analyst are **skipped slots** (tickets 15 and 19 fill them); the Editor depends on them, and a skipped dependency counts as done. One Investigator task per seed company (not one for all) so that a company's premise can be disproven on its own.
- **Tasks run as `investigation_task` jobs** (pausable) on the existing queue, not as `discover`/`extract_claims` jobs: each task's job runs the role's existing service in-process (`Scout.discover(..., run_id=)`, `ClaimExtractor.extract(job, payload)`) within the investigation's run, and in the transaction that records the outcome enqueues the next ready tasks (`JobQueue.enqueue_within`). So the DAG advances without a scheduler and a crash never leaves a task marked queued without its job. The discovery and extraction records are still created (keyed by the task's job) and readable at their own endpoints. `discover` jobs also accept a `run_id` now.
- **One run per investigation**, started by the first task (the API doesn't call LiteLLM or Hindsight). The per-run token ceiling is the investigation's `token_budget` (default `ATLAS_RUN_TOKEN_BUDGET`), enforced by the role caller before each call; the `atlas` key's `maxBudget` backstops it (a `budget_exceeded` answer is a quota failure, so it pauses).
- **Budgets.** Leads: the discovery's leads in the order found (query position, then result position), up to `max_leads` (≤ 10); the rest are counted as dropped (`lead_budget_reached`). Queries stay bounded by `ATLAS_DISCOVERY_MAX_QUERIES`. Documents: each Investigator task takes its company's **latest parsed version of each Source Document available at `as_of`**, newest first, up to what is left of `max_documents` (≤ 25, shared by all tasks). "Fetched documents" are read here from the archive: an investigation doesn't fetch leads (leads are never Evidence; ticket 09 turns them into Candidates). Rounds: `max_rounds` ≤ 2 is recorded and enforced by a check constraint; only round 1 exists until the follow-up (ticket 17).
- **Stops**, each with its reason in the investigation and a `stopped` event: the Editor's verdict (`answered` only when the Editor says so, at least one finding cites accepted Claims, and no finding was dropped as unsupported; else `needs_review`); `no_new_independent_evidence` when the round's accepted Claims bring no Evidence Family that an earlier round's didn't (in round 1: no accepted Claim), decided by code and without calling the Editor; `premise_disproven` when the Editor was cancelled because its premises or all its inputs were; `needs_review` when a task fails on its job's last attempt; `budget_exhausted` when a role call is refused for the token budget.
- **A budget stop is resumable; other stops are final.** A final stop cancels the tasks that hadn't started and finishes the run with its token totals (`run.tokens_in/out`). A `budget_exhausted` stop leaves the run open and the unfinished tasks as they were: `POST /investigations/{id}/resume` with a larger `token_budget` re-queues them (a new generation, so a new job) in the same run. A resumed Investigator task **continues** its budget-exhausted extraction (`claim_extraction.continues_id`): only the passages from the next batch on are sent, so nothing is proposed twice. Until resumed, a budget-stopped investigation's tokens are shown from its role calls, not the run row.
- **An LLM quota or outage is not a stop.** The role caller raises `TransientFailure`; the task records `task_paused` and the worker pauses the queue and requeues its job without using an attempt; `GET` shows `paused: true`. When the pause lifts, the task resumes (`task_resumed`) where it was (the extraction at its next batch, the discovery at its searches).
- **Premises and cancellation.** Every task depends on the `question` premise; each Investigator task also on `company:<slug>`. `POST /investigations/{id}/premises/{key}/disprove` (audited) cancels only the **unstarted** tasks that name the premise, then those whose every non-skipped dependency was cancelled; a running task finishes, and its findings stay in the record. Accepted Claims from a disproven company's documents are left out of the Editor's input and the disproven premises are listed on the card. Who disproves a premise besides the researcher (the Skeptic) is ticket 15.
- **The Editor adds no facts.** It is sent the accepted Claims (resolved subject, predicate, object, source; each quote as quoted low-trust data) and the leads (snippets as quoted data, never evidence). A finding must cite at least one accepted Claim of the investigation and nothing else; otherwise it is kept only as an `unsupported_finding` and the stop can't be `answered`. Each kept finding is shaped as the §7.2 claim: `claim_text` is the Editor's; `epistemic_type` is `agent_inference` (with the cited Claims' types listed); spans, Source Versions, Evidence Families (a family ID, or a lone version's ID), entity IDs and `validity_dates.evidence_available_at` are filled in by code; `needs_review` stays true until every cited Assertion is corroborated; `counterevidence_ids` is empty until the Skeptic. The card is always a draft; Hypotheses are ticket 16.
- **Metrics:** `atlas_investigation_stops_total{reason}` from the insert-only event log (a resumed budget stop stays counted). Investigation tokens appear in `atlas_llm_tokens_total{kind="investigation"}` once the run finishes.
## 2026-09-29: Hypotheses (Phase 3-6a ticket 16)

- **Saving an investigation is a Hypothesis draft by the Editor.** `POST /api/v1/hypotheses {investigation_id}` (202) needs a stopped investigation with a research card (a `no_new_independent_evidence` or `premise_disproven` stop has none: 409), one Hypothesis per investigation (409 names the existing one). It records the Hypothesis (`draft`, author = the actor, theme, related companies = the seed companies whose premise wasn't disproven) and, in the same transaction, a `draft_hypothesis` job (pausable). The API calls no LLM. The job is the **same Editor role** (calls recorded as `editor`) with its own prompt `editor-hypothesis.v1.md`, in its own run (kind `hypothesis_draft`, kept across retries on `hypothesis.draft_run_id`; the investigation's run is finished by then) under `ATLAS_RUN_TOKEN_BUDGET`. It is sent the question, the research card's findings and open questions, the investigation's accepted Claims (the card's set: none from a task whose premise was disproven) with each quote as low-trust `retrieved_data`, and the disproven premises; it proposes the §5.6/§8.1 fields (thesis statement, mechanism as §8.1's demand driver / possible constraint / economic capture question, measurable predictions, catalysts, falsifiers, required Evidence, alternative explanations) plus **unresolved questions** and **findings**.
- **Only findings state facts, and code decides what they may cite** (`atlas.hypotheses.findings`, the research card's rule): a finding must cite at least one accepted Claim of the investigation and nothing else, and its spans, Source Versions, Assertions, Evidence Families and validity dates are filled in by code (the §7.2 claim shape). Anything else is kept only as an `unsupported_finding`: **no unsupported claim is promoted.** A researcher's correction whose findings cite anything else is refused (422 `unsupported_finding`) rather than recorded. The other fields are proposals, not findings, and cite nothing.
- **Versions never change** (`hypothesis_version`): the content is a JSON object with its SHA-256 (`audit.content_hash`) beside it and its provenance (investigation, investigation run and research-card Editor call, draft run and Editor call). A trigger (`ENABLE ALWAYS`) refuses every update except the one publication stamp on an unpublished version, and every delete, so a published version is immutable in the database, not just in code. Unpublished versions don't change either: **every edit is a new version** (`POST /hypotheses/{id}/versions`, based on the latest, with a required note; audited `hypothesis.corrected` when the base is published, `hypothesis.version_created` otherwise). This is simpler than mutable drafts and makes every version diffable.
- **The §5.6 lifecycle** (`TRANSITIONS`): `draft → researching → evidence_ready`, `needs_more_evidence ↔ researching`, `evidence_ready → (publish) → reviewed → paper_tracking → closed`, `rejected` from anything before `paper_tracking`, `reviewed → needs_more_evidence | closed`; `closed` and `rejected` are final. `POST /hypotheses/{id}/transitions` (409 `invalid_transition` otherwise); `evidence_ready` needs a drafted version. **`reviewed` is reached only by publishing**: `POST /hypotheses/{id}/publish-version {version}` publishes the latest (unpublished) version from `evidence_ready` (→ `reviewed`); a correction's publication while `reviewed` or `paper_tracking` leaves the status. Every change is an insert-only `hypothesis_transition` row and an audit event (`hypothesis.transitioned`, `hypothesis.version_published` with the content hash).
- **The publish gate is pluggable** (`Hypotheses(gate=..., hooks=...)`): a check reads what it needs in the publishing transaction and returns a `GateFailure(code, message)` or None; all failures are reported (422 `publish_gate_failed`, the codes in the message). Today's gate: `no_falsifier`, `no_unresolved_question`. Ticket 20 adds the owner's approval of the Relationships the version depends on (its findings' Assertions' edges) and writes the Research Snapshot in a hook.
- **The version diff** (`GET /hypotheses/{id}/diff?from_version=&to_version=`, default the latest against the one before): a claim is a finding's statement (casefolded, whitespace collapsed) with the Assertions it cites. `new` (only later), `unchanged` (both), `contradicted` (in the earlier version, and the later one lists new counterevidence for it, or it was dropped and one of its Assertions is now disputed, rejected or superseded), and **`removed`** (dropped with no contradiction). `removed` is a fourth class beyond the spec's three: a claim a researcher drops isn't contradicted, and calling it so would misreport. Contradiction reads the Assertions' review state when the diff is read, not when the version was written (ticket 21's proposed-update flag will record contradictions as they happen). `fields_changed` names the other fields that differ.
- **The dossier export** (`GET /hypotheses/{id}/export?format=json|markdown&version=`): format `atlas.hypothesis-dossier` v1. Citations are numbered in order of first use: the Claim's exact quote and span, its Assertion (review state at the version and now), the Source Version and Document (title, publisher, canonical URL, form, accession, tier, `available_at`). Run metadata: the investigation (question, as-of, stop, budgets, run), each run behind the version (code, Hindsight and template versions, routed models, tokens) and each Editor call (prompt name, version, SHA-256, model, status). Markdown renders the same content; it includes the export time, so two exports differ in that line.
- **Relationship review is chained by the investigation** (ticket 12 left it unchained): an investigation's **final** stop enqueues `review_relationships` for the Assertions of the run's accepted Claims on its documents (≤ 100 a job, keyed `investigation:<id>:<n>`), in the stop's transaction, with a `relationship_review_queued` event before `stopped`. A `budget_exhausted` stop doesn't (the run isn't over; the resumed stop does). The review runs in **its own** `relationship_review` run, not the investigation's: the stop finishes the investigation's run in the same transaction, and a review job can call only within an unfinished run. So the review's tokens aren't counted against the investigation's token budget (the `atlas` key's `maxBudget` still backstops them). Assertions from a disproven company's documents are reviewed too: the edge's truth doesn't depend on the question.

## 2026-09-29: Claim quotes are located, not trusted

- **Why (measured).** Ticket 28's live smoke run (2026-09-29T18:25Z, MiniMax-M3 via LiteLLM, 4 Investigator calls, 18,979 tokens in / 918 out) over the recorded Coherent FY2026 10-K, Lumentum's 10-K Item 1 and an EX-99.1: **3 Claims proposed, 3 rejected `quote_mismatch`, 0 accepted**. Of the 3 quotes, **2 occur verbatim exactly once in their passage** (at other offsets than the model gave) and would have passed every later check once placed; **1 was a paraphrase**, in no passage. The Lumentum 10-K Item 1 and the EX-99.1 produced no Claims. A small sample, but offsets alone rejected every true quote, well past ticket 28's ~20% threshold. Owner decision, 2026-09-29.
- **The rule.** The model's offsets are a hint; the quote is the evidence.
  1. If the quote is exactly the passage text at the model's offsets, it is placed there (`claim.offset_source = model`).
  2. Otherwise the passage is searched for the quote as an **exact** substring: no folding of whitespace, case, quote marks or dashes. **Exactly one** occurrence: the Claim takes that span (`offset_source = located`) and every later check runs unchanged. **None**: `quote_mismatch`, as before (a paraphrase is never "found"). **More than one**: a new rejection, `quote_ambiguous` (the reason lists the occurrences); Atlas never picks one.
  3. The **Assertion span check** (`check_quote`) still runs on the final span, so an accepted Claim's Assertion is always an exact span of the archived parsed text.
- **Recorded.** `claim.offset_source` (migration 0024; null when the quote was never placed, and for Claims recorded before 0024), shown by `GET /api/v1/claims[/{id}]`. The model's own offsets stay in `claim.proposed`, so how often it counts right stays measurable (`offset_source` counts `model` vs `located`).
- **Scope.** Only within the one passage the Claim names: a quote is never moved to another passage or elsewhere in the document. The earlier out-of-passage check (`quote_outside_passage`) still runs first on the model's offsets.
- **Not changed:** researcher-created Assertions (`POST /api/v1/assertions`) still need exact offsets; the viewer computes them from the selection.

Resolutions are cached per job by (normalized name, ticker, MIC).
- **A Candidate is a (theme, company) pair** (CONTEXT.md), keyed by `cik:` when the resolution has an entity with a CIK, else `lei:`, else `name:` + the normalized name (a conflict, several matches, or a listing with no issuer record). A later lead naming the same company in the same theme joins it (`lead_mention`), whatever the Candidate's state; it is never re-proposed. The resolution is stored whole. A CIK-keyed Candidate doesn't carry the LEI the resolver linked by name: that CIK↔LEI link stays the owner's (ticket 02). Country: GLEIF's jurisdiction, else `US` for an SEC US state of incorporation, else none.
- **When:** each `discover` job enqueues `propose_candidates` (key `discovery:<id>`, same job class) when `ATLAS_SEC_USER_AGENT` is set, since resolution calls SEC; otherwise nothing is enqueued (and `atlas jobs enqueue propose_candidates` refuses at run time with that reason). An investigation's Scout (ticket 14) calls the discovery directly and so enqueues no proposal; its leads can be proposed by hand. A lead is examined once (`lead_examination`), so a retried or repeated job reads only new leads. The role calls are one run of kind `candidates`, finished when the attempt ends. Pausable (LiteLLM); an identity-source failure is an ordinary failed attempt.
- **Nothing commits automatically.** The owner's commit (only from `lead`) creates the `company` row with the ID a config entry would get (UUIDv5 of the CIK, else the slug; `atlas.companies.company_id_from`), adds `universe_company` (theme, company, Candidate), and moves the Candidate to `investigating`, all audited in one transaction. The slug defaults to the name's lowercase words joined by `-`; the owner may set slug, display name, country (required when resolution found none: 409 `country_required`), layer, and for a name-only Candidate one of the CIKs its resolution offered (409 `cik_not_offered` otherwise). 409 `already_in_universe` when the CIK is a company's already, `slug_taken` when the slug is.
- **The universe's database extension:** `extend_universe(connection, universe)` adds each `universe_company` company that has a source path to the config's companies (config wins on a slug) and to its theme's members. The `ingest` job (for a slug the config lacks), `atlas ingest` and retention (theme tags) use it; other readers of the theme config (the research scope, discovery themes) are unchanged, since a commit adds no theme.
- **Source path at commit:** a resolved CIK makes the company `sec` and enqueues its `ingest` (key `candidate-commit:<id>`, looking back `ATLAS_INGEST_LOOKBACK_DAYS` like `atlas ingest`) in the commit's transaction. Without a CIK the company has no source path and the Candidate's `ingest_note` says no automated source exists yet: exchange feeds need a config entry (issuer code, feed ID) and a register decision, so a committed non-SEC company is added to the config by hand when its source is ready.
- **Rejected Candidates are kept** with their reason (`rejected`, CHECK: reason set exactly then). Candidates are never deleted: `candidate_no_delete`/`candidate_no_truncate` triggers, and the runtime role has no DELETE. Commit and reject apply only to a `lead`; the other §8.3 transitions (evidence_ready, needs_more_evidence, paper_tracking, closed, and rejecting a committed one) are later tickets' (the research workflow).
- **Metric:** `atlas_candidates{state}`, a gauge over all seven states.
## 2026-09-29: Quota-window pacing and the staged rollout (Phase 3-6a ticket 27)

- **Two providers, two units.** Job kinds are classified by whose subscription they spend (`atlas.jobs.budget.PROVIDER_KINDS`): the Hindsight-backed kinds (`retain`, `poll_operation`, `reprocess`, `refresh_mental_model`, `reflect`) are `codex`; the LiteLLM role kinds (`discover`, `extract_claims`, `review_relationships`, `investigation_task`) are `minimax`. `ingest` and `noop` spend neither. Codex is counted in **Hindsight operations submitted** (retain and reprocess batches, 1 each; `hindsight_operation` rows), because Atlas can't see the shared server's Codex tokens. MiniMax is counted in **recorded tokens** (`llm_call.tokens_in + tokens_out`), what the per-run budget already counts.
- **Rolling window, pacing clock.** Each unit counts from when the queue first sees its row until one window later (`ATLAS_BUDGET_WINDOW_HOURS`, default 5). Every claim first records unseen rows in `provider_usage` at the pacing clock's now (`INSERT … ON CONFLICT DO NOTHING`, so concurrent workers count each once), then sums each provider's window. Recording at the pacing clock rather than the rows' own database timestamps keeps the budget on the same injectable clock as the pause and the window. Migration 0028 records existing rows at their own times, so history isn't counted as spent on deploy. The queue view counts rows not yet seen as spent now, without writing.
- **Holding rule.** A job of a budgeted kind is claimed only while the window's usage is **below the limit for its class**: the budget for `interactive`, `floor(budget × (1 − ATLAS_BUDGET_INTERACTIVE_RESERVE))` for `backfill` (default reserve 0.3). The cost of the next job is unknown until it runs, so a job may overshoot by what it spends (one batch; at most `ATLAS_RUN_TOKEN_BUDGET` tokens for a role run). With several workers, each may overshoot once. `poll_operation` is never held: it spends nothing new and holding it would only delay observing a submitted batch (the same reason it's always interactive). Budgets apply whether or not a backfill window is set; the 429/outage pause stays the backstop for what the budget doesn't foresee.
- **Conservative defaults**, tuned by the owner: `ATLAS_CODEX_BUDGET_OPERATIONS=40` (backfill 28) and `ATLAS_MINIMAX_BUDGET_TOKENS=400000` (backfill 280,000) per 5 h. The 2026-09 bootstrap submitted 1,397 operations in minutes; 40 per window is about 3% of that. `docs/runbooks.md` ("Universe rollout and quota budgets") says how to read the budget view and when to raise them.
- **The backfill window is optional and may list ranges.** `ATLAS_BACKFILL_WINDOW` defaults to empty (any time) and accepts comma-separated `HH:MM-HH:MM` ranges (`01:00-07:00,13:00-15:00`). The next opening is the earliest range start after now.
- **Ingest plan.** A backfill SEC ingest of a company with no Source Version yet records an `ingest_plan` after discovery and before any fetch: every discovered document (after the lookback and 8-K selection), their count, and the estimated retain operations (one per `sec_filing_document`; companyfacts is normalized, not retained). One per job; audited. It isn't a gate: the ingest proceeds, bounded by the cap and the budget. Exchange ingests record no plan yet (Innolight is manual import; IQE and Soitec wait for tickets 05/06).
- **Retain cap.** `atlas ingest --max-retains N` (SEC filers only) retains at most N of the company's **not-yet-retained** versions (each document's latest version, retainable parse and language, no memory documents, no `retain` job), newest `available_at` first, ties by ingest order. The rest are listed as `retains_deferred` in the job's artifacts; the next capped ingest (a new `--key`) retains the next N, so a company's backfill can be rolled out over several windows without re-fetching.
- **Visibility.** `GET /api/v1/queue` adds `budgets` (per provider: unit, window, used, budget, backfill limit, whether each class is held, when each resumes, the kinds held) and `budget_held` per pending kind. `GET /api/v1/ingest-plans[?company=]` lists plans. Metrics: `atlas_budget_used{provider,unit}`, `atlas_budget_limit{provider,job_class}`, `atlas_budget_window_seconds`, `atlas_budget_usage_total{provider}` (`increase(...[5h])` gives usage per window) and `atlas_queue_jobs_held_by_budget{provider,kind,job_class}`.

## 2026-09-29: No personal data in the User-Agent of non-SEC sources

SEC's EDGAR access rules require a User-Agent with a contact email, so `ATLAS_SEC_USER_AGENT` keeps one. Every other source (the exchange adapters, and any later non-SEC HTTP source) sends the generic `ATLAS_EXCHANGE_USER_AGENT` (default `AtlasResearch`). ## 2026-09-30: Scenarios and the Financial Analyst (Phase 3-6a ticket 19)

- **The model** (`atlas.scenarios.model`, `scenario-v1`) is §8.2 with ticket 12's BOM share as an explicit input: `component_price = downstream_unit_price × bom_share`; `incremental_revenue = addressable_units × company_share × component_price`; `incremental_contribution = revenue × operating_margin`; `scenario_enterprise_value = contribution × ev_multiple`; `net_debt = total_debt − cash`; `illustrative_equity_value = EV − net_debt`; `equity_value_per_share = equity / diluted_shares`; and `revenue_exposure = incremental_revenue / reported_revenue` (the exposure against the company's size). §8.2's "scenario enterprise value − net debt" subtracts the whole company's net debt from the incremental EV; it is kept as written and labelled illustrative. It is a pure function: no LLM, database or clock. No PyMC.
- **Inputs.** Each of the ten inputs has low, base and high values (low ≤ base ≤ high, within the input's bounds: fractions 0–1, margin −1–1, divisors above 0) and is `sourced` (an XBRL observation or an Assertion), `estimated` (with a non-blank basis) or `missing`. **A value with neither a source nor a basis doesn't validate** (Pydantic, 422 `invalid_request`). An input left out is missing. A missing input blocks every line built on it, which names the missing inputs; nothing is filled in.
- **A source must stand at the cutoff** (`atlas.scenarios.sources`, 422 `invalid_scenario` listing each problem): an XBRL observation must be the company's **as-of** observation for its period key at the cutoff (ticket 18's selection: the latest periodic filing with `available_at ≤ as_of`; so a value a later filing restated or reaffirmed, or one not yet available, is refused); only a currency amount (revenue, debt, cash) or a share count may be XBRL-sourced; it must be in the table's currency (or `shares`), since currencies are never mixed without an FX basis; and its value must equal the input in every case (a sourced figure isn't a range). An Assertion must exist, be available at the cutoff (its Source Version's `available_at`) and not be rejected or superseded; its number can't be checked mechanically, so its quote is shown beside the value. The cutoff is the investigation's `as_of` unless the request gives one.
- **Determinism.** `Decimal` in a fixed context (precision 50, half-even); every line rounded half-even to 6 places; every number a plain decimal string (no exponent, no trailing zeros, no negative zero); outputs are canonical JSON (sorted keys, `,`/`:` separators, UTF-8), stored as that text and hashed (SHA-256). The same table, however it was written (JSON numbers or strings, trailing zeros, key order), gives the same bytes. Each read recomputes the stored table and reports `recomputes_identically`.
- **Sensitivity**: each present input of the base case moved −20% and +20% alone, every line recomputed; a fraction or margin pushed past its bound is clamped and marked `capped`.
- **Attached to a Hypothesis version**, insert-only (`scenario`, audited `scenario.created`). A scenario may be attached to a published version (the version itself doesn't change). The company must be one of the Hypothesis's related companies.
- **The Financial Analyst fills the plan's slot** (`roles/financial_analyst.py`, prompt `financial-analyst.v1.md`): after the Investigators, with the accepted Claims (by Assertion ID; quotes as low-trust retrieved data) and, per seed company an accepted Claim names, its as-of XBRL figures (per metric the latest *reported* value, an annual one for a flow metric where there is one; derived quarters aren't sent because a sourced input cites one observation). One call proposes a table per company. Code keeps an input only if it validates on its own and its source stands **and was sent** (an observation of that company's figures, an Assertion of the Claims); anything else becomes `missing` with `rejected: <reason>` and is listed in the task's `rejected_inputs`. With no accepted Claim naming a seed company it is skipped without an LLM call. The tables go in the task's artifacts; `POST /hypotheses/{id}/scenarios {version}` without `assumptions` turns them into scenarios (re-checked at the cutoff: a source that no longer stands becomes missing), with the task and role call as provenance. The researcher's own table (with `assumptions`) is the analyst override; it is refused rather than downgraded when a source doesn't stand.
- **Not built:** a market-data as-of (§5.7's "market-data as-of"): there's no market-data provider (Phase 6b), so a multiple is always an estimate; the metric `atlas_scenario_runs` (spec story 54) is left to the metrics ticket.
